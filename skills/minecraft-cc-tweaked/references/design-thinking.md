# 设计思路：从需求推导程序

> 本文件教的是**怎么想**，不是给出可以照抄的成品。`templates.md` 中的程序只是某一组约束下的一个答案；用户的约束（设备、外设、规模、网络、安全、服务器 TPS）一变，答案就该变。先按本文件推导，再用模板核对写法。

## 一、推导流程（六步）

1. **翻译成 CC 原语**：需求里的每个名词、动词对应什么？
   - 输入从哪里来：按键/触摸（事件）、外设状态（轮询方法）、红石（事件 + 读取）、网络消息（事件）、时间（计时器）。
   - 输出到哪里去：外设方法（搬运、显示、发声）、红石、网络消息、文件。
   - 需要记住什么：内存状态（重启即丢）还是持久状态（文件）。
2. **列约束**：对照第二节逐条问"这一条对本需求有没有影响"。
3. **选结构**：一次性脚本、轮询循环、事件循环、多协程、状态机、多台计算机分工（第三节）。
4. **失败模式分析**：对每个外部交互回答第四节的五个问题，决定检查、重试、超时、降级。
5. **设计可观测性**：用户怎么知道它在正常工作？状态行、计数器、日志、启动自检、声音提示。
6. **增量验证计划**：先在 `lua` 交互环境验证单个调用的返回值 → 写最小可运行版本 → 再加功能。告诉用户每一步怎么验证。

交付时把关键决策写给用户（"用事件循环而不是 sleep 轮询，因为要同时响应触摸"），这样用户换了条件也知道该改哪里。

## 二、CC 世界的硬约束清单

| 约束 | 影响什么决策 |
|---|---|
| 时间粒度 0.05 秒（1 刻）；`sleep`/计时器向上取整 | 不要设计需要更细时间精度的逻辑 |
| 服务器 TPS 会下降，游戏刻变慢 | 需要跟真实时间对齐的逻辑（音频、外部网页）按 `os.epoch("utc")` 计算，而不是数刻 |
| 外设方法通常要等一刻才返回 | 大量调用要并发或缓存；不要在一个循环里调用成千上万次 |
| 长时间不让出会被终止 | 计算密集的循环要定期让出 |
| 事件只会交给正在等待的代码；带过滤的等待会丢弃其他事件 | 程序里等待事件的地方越少越好（见模式 1） |
| 事件队列 256 个 | 高频事件源（网络音频帧、大量并发请求）要控制速度 |
| 区块卸载 = 关机，内存清空 | 长任务要持久化进度并从 `startup.lua` 恢复 |
| 外设可能随时被拆、编号可能变 | 名字可配置；调用防断开；监听接入/断开事件 |
| 网络不可靠：丢包、延迟、超时、服务器禁用 HTTP | 超时、有限重试、降级 |
| rednet 可被监听和伪造 | 敏感命令要认证（见 `security.md`） |
| 磁盘约 1 MB，内存有限 | 不缓存大数据，或只缓存少量 |
| 终端只有 256 个字符，没有中文 | 界面文字用英文/拼音或专用渲染方案 |
| 能接触方块的玩家可以拆机器、读文件 | 秘密不放在终端上（见 `security.md`） |

## 三、程序结构怎么选

| 情况 | 结构 | 理由 |
|---|---|---|
| 做一件事就结束（挖一条隧道、整理一次箱子） | 一次性脚本 | 最简单；失败时打印原因退出 |
| 周期性检查，不需要响应输入 | `while true do 工作() sleep(N) end` | 简单可靠；`sleep` 丢事件在这里无所谓 |
| 要响应多种事件（触摸、按键、消息、红石）并且要定时 | 单个事件循环 + 计时器 | 所有事件都经过同一个 `os.pullEvent()`，一个都不丢 |
| 几个**互相独立**的长期任务（工作循环 + 命令控制台 + 网络监听） | `parallel.waitForAny/All` | 每个任务写成直线代码，互不干扰；任务之间通过共享表或自定义事件通信 |
| 有明确阶段（空闲 → 工作中 → 完成/出错），且要能从中断恢复 | 状态机 + 状态持久化 | 当前状态写入文件，重启后读取并"对账"（见模式 6） |
| 一台计算机做不完或需要分散在多处 | 多台计算机 + 消息协议 | 每台职责单一；协议要有类型、版本、超时（见模式 9） |

## 四、失败模式分析：每个外部交互都问五个问题

对每一次外设调用、海龟动作、网络请求、文件读写，问：

1. **失败了怎么办？**（返回 false/nil、抛错）→ 检查返回值；需要时 `pcall`。
2. **一直不回来怎么办？**（网络挂起、机器卡住）→ 超时/看门狗计时器。
3. **对象消失了怎么办？**（外设被拆、文件被删、服务器关闭 HTTP）→ 重新查找、降级、提示用户。
4. **重复或乱序怎么办？**（消息重发、旧响应晚到、用户连点）→ 请求标记、序号、幂等操作。
5. **做了但没生效怎么办？**（命令发出去了，机器没反应）→ 执行后读状态验证，有限次重试（见模式 4）。

答案不一定都要写成代码，但要**有意识地决定**：有的失败可以直接报错退出，有的必须自动恢复。

## 五、思路模式库

每个模式只给出思路与最小骨架，写代码时按实际需求展开。

### 模式 1：单一事件等待点 + 自愈计时器

- **问题**：程序里多处 `os.pullEvent("某事件")`、`sleep`、`rednet.receive`，结果某处等待时把别处需要的事件吞掉了（计时器事件丢失后，周期任务永远停止）。
- **关键思路**：整个主循环只有**一处**不带过滤的 `os.pullEvent()`，所有事件都在这里分发；其余代码只做"处理一个事件就返回"的工作，从不自己等待。计时器在每轮循环开头检查"是否已武装"，未武装就重新启动——即使某次事件被外部 API 吞掉，下一轮也会自动恢复。
- **取舍**：代码要拆成回调式的小函数，状态放在表里；比直线代码难写，但最可靠。任务彼此独立时用 `parallel` 更简单。
- **坑**：调用会内部等待的 API（`http.get`、`rednet.receive`、`sleep`）就破坏了这个结构——改用异步版本（`http.request`、直接处理 `rednet_message` 事件）。

```lua
local timers = {}
local function arm(name, seconds)
    if not timers[name] then timers[name] = { id = os.startTimer(seconds), seconds = seconds } end
end

local handlers = {
    tick = function() print("tick", os.clock()) end,
    report = function() print("report") end,
}

while true do
    arm("tick", 1)
    arm("report", 5)
    local event, p1 = os.pullEvent()               -- 唯一的等待点
    if event == "timer" then
        for name, t in pairs(timers) do
            if t.id == p1 then
                timers[name] = nil                 -- 下一轮自动重新武装
                handlers[name]()
            end
        end
    elseif event == "key" and p1 == keys.q then
        break
    end
end
```

### 模式 2：按真实时间节拍，而不是按刻数

- **问题**：外部世界（浏览器、音频、现实时钟）按真实时间运转；服务器 TPS 从 20 掉到 14 时，"每刻处理一次"的逻辑就慢了 30%，积压越来越多。
- **关键思路**：用 `os.epoch("utc")`（毫秒）计算"从基准时间到现在应该处理多少份"，减去已经处理的份数，就是这一轮要补的量；每轮补的量设上限，防止长时间卡顿后一次性爆发。
- **坑**：时钟可能跳变（回退或长时间暂停），检测到异常就重新对齐基准。

### 模式 3：有界缓冲，溢出丢最旧

- **问题**：实时数据（语音、传感器读数、状态广播）的生产速度可能暂时超过消费速度，无界队列会让延迟越来越大、内存越来越多。
- **关键思路**：用固定容量的环形队列；只保留"目标积压量"（例如 0.3 秒的数据），超出就丢**最旧**的——实时场景里旧数据最没价值。另设一个物理上限做护栏。统计丢弃数量供观察。
- **取舍**：丢数据换低延迟。非实时数据（物流任务、账本）恰恰相反，绝不能丢，要排队或反压。

### 模式 4：执行 → 验证 → 有限次重试

- **问题**：给机器发红石脉冲、把物品放进机器、发出网络命令后，**不能假设它生效了**。
- **关键思路**：每个动作之后读取可观察的状态（物品栏内容、储能、方块状态、对方回执）确认结果；没生效就重试，设最大次数，超时后报错而不是无限等待。
- **骨架**：

```lua
local function act_and_verify(act, check, tries, interval)
    for _ = 1, tries do
        act()
        sleep(interval)
        if check() then return true end
    end
    return false
end

local chest = peripheral.find("inventory")
local ok = act_and_verify(
    function() redstone.setOutput("back", true) sleep(0.1) redstone.setOutput("back", false) end,
    function() return chest ~= nil and next(chest.list()) ~= nil end,
    10, 0.5)
print(ok and "machine responded" or "no response after 10 tries")
```

### 模式 5：数据驱动的规则，而不是写死的代码

- **问题**：仓储、物流、分拣的需求会不停变化（新增箱子、调整优先级、黑白名单），每次都改代码容易出错。
- **关键思路**：把"做什么"写成数据（任务表：来源、目标、过滤、数量、优先级），代码只负责"解释并执行规则"。外设名支持通配符（如 `minecraft:chest_*`），新加的箱子自动纳入。可以提供一个命令控制台（与工作循环 `parallel` 运行）在运行时增删规则并保存。
- **取舍**：前期多写解释器代码；规则格式要在读取时校验，错误规则只跳过该条并报告。
- **坑**：每条规则的执行用 `pcall` 隔离，一条规则出错不应该让整个系统停下。

### 模式 6：既是来源又是目标的容器——防止"乒乓"

- **问题**：缓冲箱同时作为输入和输出时，刚送进去的物品下一轮又被当作输入搬走，物品在容器之间来回移动。
- **关键思路**：记录"本系统送进该容器的物品"（按槽位和数量的快照），这些物品不再作为输入；快照与实际内容不一致时（被别处取走或消耗）再清除记录。更简单的替代：让输入与输出的过滤规则互斥，或者把缓冲箱拆成"入口箱"和"出口箱"。

### 模式 7：持久化状态 + 启动对账

- **问题**：程序在"已经放出物品/打开阀门/移动一半"时断电，重启后不知道现实世界处于什么状态。
- **关键思路**：每次改变外部世界之前/之后把"意图"和"已完成的状态"写入文件；启动时读取记录，再读取真实世界（物品栏、红石、GPS 坐标）对比，必要时先回到安全状态再继续。
- **坑**：写文件和动作之间仍可能断电，所以启动时必须以**真实世界**为准，文件只是线索。

### 模式 8：启动自检与可观测性

- **关键思路**：
  - 启动时检查所需外设是否在预期位置、类型是否正确，缺失就**立刻**报出清楚的错误（"front 需要空间 IO 端口，当前是 nil"），而不是运行到一半才出错。
  - 能自测的部分先自测：扬声器先播一声测试音、网络先 ping、数据结构先做一次读写。
  - 运行中维护计数器（处理数、失败数、丢弃数、队列深度、空转次数），在终端最后一行实时显示，并定期写一行日志——出问题时用户能直接告诉你数字。
  - "收到了输入但一直没有输出"这类异常状态可以自动检测并提示。

### 模式 9：多台计算机之间的协议

- **关键思路**：
  - 每条消息是表：`{ type = "...", version = 1, id = 请求号, ... }`；接收端先判断 `type`，未知类型忽略。
  - 请求-应答要带请求号，应答原样带回；客户端设超时，超时就重试或报错。
  - 广播/中继场景里会收到**自己发出的消息的回声**，要识别并忽略。
  - 状态与控制分开：状态（周期广播，丢了无所谓）和命令（需要应答、需要认证）走不同协议名或信道。
  - 保留一个最简单的**备用控制端**（不依赖复杂界面），主控端坏了也能执行关键操作（如紧急停机）。
  - 命令要做权限检查（见 `security.md`）。

### 模式 10：程序之间用自定义事件通信

- **问题**：同一台计算机上的后台服务（播放器、网络监听）和前台界面要互相控制。
- **关键思路**：用 `os.queueEvent("myapp_command", 实例id, 参数...)` 发命令，服务端在事件循环里处理并用 `os.queueEvent("myapp_status", 实例id, 状态...)` 回报；带实例 id 区分多个实例。事件参数不能含函数。
- **同理可做远程输入**：把一台计算机的 `key`/`char`/`mouse_*` 事件通过 rednet 发给另一台，接收端 `os.queueEvent` 重放，大屏程序就能被远程操作——但接收端必须验证发送者，否则任何人都能"替你打字"。

### 模式 11：命令行接口

- 参数用 `local args = { ... }` 解析，支持 `--name value` 和 `--name=value`；缺参数或参数非法时打印用法并 `return`，不要让程序带着 nil 继续运行。
- 数值参数用 `tonumber` 并限制范围；必需的外设/API 不可用时（`http` 为 nil、找不到扬声器）先给出原因再退出。

### 模式 12：功能探测与降级

- 新版本 API、可选库、附属模组提供的方法：用 `type(x) == "function"` 或 `pcall(require, ...)` 判断，存在就用更好的实现，不存在就退回基础实现，并告诉用户缺了什么。
- 降级也是设计的一部分：HTTP 不可用时用本地文件；高级显示器不可用时用终端；GPS 不可用时用相对坐标。

## 六、评审别人代码/教程的方法

网上教程、论坛代码、AI 生成的代码经常"看起来对"。逐项检查：

1. **每个函数都存在吗？** 对照 `api-reference.md`/tweaked.cc。常见的编造函数：`textutils.sha256`、`os.exit`、`turtle.getPosition`、`peripheral.getAll`。
2. **调用方式对吗？** `.` 还是 `:`；参数顺序；返回值个数（如 `turtle.getItemDetail` 只返回一个值）。
3. **环境假设对吗？** `os.run` 启动的程序没有 `shell`；`shell`/`multishell` 不在 `_G` 里；`require` 的路径规则。
4. **会不会丢事件、会不会长时间不让出？**
5. **失败路径有没有处理？**（第四节的五个问题）
6. **安全声明是否成立？** 声称"安全"的方案，用 `security.md` 的威胁模型逐条检验。
7. **翻译与摘要可信吗？** 机器翻译的 API 说明可能错得离谱（把 up 译成"往前"），官方摘要偶尔也有笔误；以函数实际行为和完整文档为准。

## 七、一个完整推导示例

**需求**："基地门口装一个显示器，显示仓库里钻石数量，低于 64 个时亮红灯。"

1. **原语**：输入 = 网络上所有物品栏的 `list()`（轮询）；输出 = 显示器文字 + 红石输出；状态 = 无需持久化。
2. **约束**：箱子可能很多 → 扫描要并发、频率不必高（10 秒一次足够）；显示器可能是普通显示器 → 不依赖颜色；外设可能增减 → 每次扫描重新 `find`。
3. **结构**：只有周期任务、不响应输入 → `while true do scan() draw() sleep(10) end`。
4. **失败模式**：某个箱子扫描时被拆 → `pcall` 跳过该箱子；没有显示器 → 启动时报错；扫描很慢 → 分批并发。
5. **可观测性**：显示器上显示"上次更新时间"和扫描的箱子数，用户能看出程序是否还活着。
6. **验证**：先在 `lua` 里试 `peripheral.find("inventory")` 的数量和某个 `list()` 的内容，再运行完整程序。

如果需求变成"玩家点击显示器可以切换显示的物品"，第 3 步就要换成事件循环（触摸事件 + 计时器），而不是在原程序上硬加 `os.pullEvent`——这就是"按约束推导"而不是"改模板"。

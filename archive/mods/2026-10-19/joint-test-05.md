# 联合测试 5：待按 mod 整理的经验

来源：[本次核验报告](https://github.com/EvergardenRoxy/CC-Tweaked_MCP/blob/88c3e7721d334426e01155abafa8e1cec335cb86/docs/testing/reports/05-precision-mechanism.md)。本文件是提取记录，没有再次连接用户游戏，也没有修复交付程序。

## 实际环境与操作者修改

- Minecraft 1.21.1 / NeoForge、CC:T 1.120.2、Create 6.0.10、AP 0.8.2a、cct-run/cct-live 0.2.4。
- 用户确认一个 depot＋一个 deployer，工件留在 depot，依次供三种辅料，重复五轮。停止供应辅料即暂停，已进入机械手的一份仍可能完成动作。
- 明确要求翻牌屏中文显示四种原料和成品库存。不能用旧三机械手方案或原生 CC 字库限制取代这一要求。
- 用户要求有疑问时先问；实机断线演练被用户主动跳过，应保留未测标记。

## Create：已确认与需要纠正的结论

- 会话读到的 jar 基础配方为三步序列、loops=5，精密构件权重 120 / 总权重 150，即整件终态 80%；不是每轮一次独立的 80%。没有导出服务器最终 recipe manager/数据包覆盖，不把 jar 基础配方当成所有整合包的保证。
- 九类终态为一类成品和八类失败结果。旧交付文档写“其他九种”有误；取消移出的半成品也不能计作随机失败产物。
- 真实加工、按成品补产、选定检查点恢复有证据；不能扩大成任意崩溃位置恢复通过。R002 是十次尝试、八成功、二失败，小样本不能用来证明概率。
- 显示链接器 `getSize()` 的字节码先返回 maxRows，再返回 maxColumns；本次 8,17 是八行十七列。原 Skill 的旧笔记已经正确写了行数在前，错误在测试执行时反读，不应记录为 API 不可信。
- 同一个实例写出八行有记录，缺乏“每行必须一个链接器”的证据。需要区分来源、目标起始行、目标尺寸和刷新能力。
- `writeBytes` 接受字节表的路径有实现和现场确认；显示刷新、转速与物理链接设置仍需按版本/现场核对。

## Advanced Peripherals：保留的现场事实

- 中文聊天与回复有玩家确认和截图；本次使用 JSON Unicode 转义的 formatted-message 路径。通道可行不代表所有 AP 版本/所有发送方法一致。
- 实际适配器把 `sendFormattedMessage` 返回 false/cooldown 包装成成功；这是上传 Lua 程序的错误，不据此判模组接口异常。
- 测试里把 Mock 的发送函数替换成 false，绕过真实适配器，因而漏掉这个错误。后续专用测试应覆盖真实适配器和实际非零冷却。

## 跨模组证据与未测边界

- 库存工具预览只显示五十项，另有 `101 more`；不能从可见项推算保险库全部数量。应在完整列表上聚合，并注明玩家取放和生产时序的影响。
- 三套原脚本合计 310 条断言通过，但六类新增探针仍复现备份、损坏状态、保存失败、发送结果、队列/日志与显示失败问题。它们属于交付应用，不是原 MCP 仓库的 95 条审查问题。
- 开工前缺料不等于第三轮缺料；depot 预占不等于输出满库；第二轮附近重启不等于终态转移窗口恢复。十个不同 ID 的真实突发请求、实际确认延迟、关键外设断线和完整 trace/卸载矩阵均不能补写成已通过。
- `state.log` 上限与磁盘 `events.log` 是不同对象；前者 120 条不表示后者已经轮换。
